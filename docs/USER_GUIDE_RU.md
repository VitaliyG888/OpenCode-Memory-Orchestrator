# Подробная инструкция: Memory Intelligence и AI Development Orchestrator для OpenCode

Версия инструкции: 0.5.0  
Назначение: установить, настроить и ежедневно использовать два независимых OpenCode V2-плагина, которые работают с одной проектной памятью.

---

## 1. Что входит в систему

В комплект входят три технических пакета, но два OpenCode-плагина:

1. **Memory Intelligence** — самостоятельная система долговременной памяти. Она хранит исходные контрольные точки, заметки, факты, решения, сущности, связи, противоречия, embedding-векторы и историю проекта.
2. **AI Development Orchestrator** — потребитель Memory Intelligence. Он управляет проектами, задачами, зависимостями, сессиями и декомпозицией работы.
3. **Memory Intelligence Core** — общая библиотека и сервисный слой. Это не третий OpenCode-плагин. Оба плагина используют один объект клиента и одну базу данных.

Оба плагина работают в рамках одного проекта и используют базу:

```text
.orchestrator/orchestrator.sqlite
```

Копия базы для каждого плагина не создаётся. Обычные агенты OpenCode могут пользоваться `memory_*` независимо от наличия Orchestrator.

## 2. Главное отличие: сессия сохраняется автоматически

Memory Intelligence проверяет накопление токенов по завершении каждого взаимодействия с агентом. В OpenCode V2 основными триггерами служат терминальные события `session.execution.succeeded`, `session.execution.failed` и `session.execution.interrupted`; `session.idle` остаётся дополнительным совместимым триггером. Проверка запускается после завершения ответа/цикла инструментов, а не посреди генерации. События V2 читаются из `event.data` (для старых форматов сохранён fallback на `event.properties`).

По умолчанию порог равен **50 000 токенов**.

Когда накопленное потребление достигает порога:

1. Плагин читает сохранённую историю активной OpenCode-сессии из локальной базы OpenCode в режиме read-only.
2. Считает потребление токенов. При наличии статистики провайдера учитываются `input`, `output`, `reasoning`, `cache.read` и `cache.write` из метаданных завершённых assistant-сообщений.
3. Сравнивает общий показатель с количеством токенов, сохранённым на предыдущей контрольной точке. Следующий порог отсчитывается от предыдущего успешного сохранения.
4. Создаёт идемпотентный запуск автосохранения и сохраняет полную исходную транскрипцию в `checkpoints` до удалённого анализа.
5. Выделяет сообщения, появившиеся после предыдущей успешной автоматической контрольной точки.
6. Делит новый фрагмент на части, чтобы не превысить лимит входного текста Memory Intelligence.
7. Анализирует новые части через модель, настроенную в `memory.config.json`.
8. Проверяет извлечённые сущности, факты и решения на дубликаты.
9. Создаёт новые объекты знаний. Уже известные объекты не дублируются — к ним добавляется связь с новым источником доказательства.
10. Сохраняет статистику автосохранения и передвигает курсор до последнего обработанного сообщения.

Если анализ не удался, исходная контрольная точка уже сохранена. Запуск помечается как ошибочный и может быть повторён при следующем терминальном событии выполнения. Идемпотентные хэши фрагментов позволяют повторно запустить обработку без создания дублирующих объектов.

### 2.1. Как именно считаются токены

- **Основной режим — session usage OpenCode.** Если `ctx.session.get()` возвращает накопленную статистику `tokens`, берётся `input + output + reasoning + cache.read + cache.write`.
- **Первый резерв — message-level provider usage.** Если агрегированная статистика недоступна, суммируется usage каждого сохранённого assistant-сообщения (`metadata.assistant.tokens` для актуального V2 Message API, плюс совместимые форматы старых версий). Одно и то же сообщение считается один раз.
- **Второй резерв — оценка текста.** Если usage не сохранился ни в сессии, ни в сообщениях, приблизительное число токенов оценивается по объёму текста: примерно один токен на 3,6 символа. Это эвристика, не точный токенизатор.
- Если `estimateFallback` выключен, автосохранение не запускается, пока недоступна реальная usage-статистика.
- Порог относится к **суммарному потреблению модели за историю сессии**, включая повторно передаваемый контекст, а не к текущей длине контекстного окна.
- Сохранение запускается на ближайшем событии завершения выполнения после пересечения порога. Если один ответ резко превысил порог, выполняется один снимок актуального состояния; затем следующий порог отсчитывается от этого успешно сохранённого значения.

### 2.2. Где настраивать порог

Открой файл:

```text
.opencode/orchestrator.config.json
```

Секция по умолчанию:

```json
{
  "memory": {
    "autoSave": {
      "enabled": true,
      "tokenThreshold": 50000,
      "checkOnSessionIdle": true,
      "saveRawTranscript": true,
      "extractNewObjects": true,
      "estimateFallback": true,
      "maxTranscriptCharsPerChunk": 38000
    }
  }
}
```

Параметры:

| Параметр | Значение по умолчанию | Описание |
|---|---:|---|
| `enabled` | `true` | Полностью включает/выключает автоматическое сохранение. |
| `tokenThreshold` | `50000` | Количество новых накопленных токенов между успешными авто-сохранениями. Допустимый диапазон: 1 000–2 000 000. |
| `checkOnSessionIdle` | `true` | Историческое имя параметра для совместимости; проверка выполняется после завершения хода агента по terminal events V2. |
| `saveRawTranscript` | `true` | Сохранять исходную транскрипцию в SQLite до анализа. Рекомендуется оставить `true`. |
| `extractNewObjects` | `true` | После checkpoint извлекать из нового фрагмента сущности, факты, решения, риски и вопросы. |
| `estimateFallback` | `true` | Использовать оценку по тексту, если точная usage-статистика отсутствует. |
| `maxTranscriptCharsPerChunk` | `38000` | Максимальный размер части транскрипта для анализа; внутри плагина ограничивается безопасным диапазоном 3 000–43 000 символов. |

Примеры:

**Автосохранение каждые 25 тысяч токенов:**

```json
"tokenThreshold": 25000
```

**Автосохранение каждые 100 тысяч токенов:**

```json
"tokenThreshold": 100000
```

**Выключить авто-сохранение:**

```json
"enabled": false
```

После изменения файла перезапусти OpenCode, чтобы плагины перечитали конфигурацию.

> Конфигурация порога находится именно в `.opencode/orchestrator.config.json`. Настройки embedding- и intelligence-моделей, API URL и ключи находятся в `.opencode/memory.config.json`. `readMemoryConfig()` также понимает значения из старого `orchestrator.config.json` для обратной совместимости.

## 3. Проверка статуса

В любой сессии выполни:

```text
/memory-status
```

В ответе должны присутствовать:

- статус Memory Intelligence;
- провайдер и embedding-модель;
- доступность векторного индекса;
- текущая конфигурация `autoSave`;
- последние сессии, сохранённые автоматически;
- количество запусков, завершённых/ошибочных;
- настройки `recall`, privacy redaction и semantic deduplication.

Отдельный отчёт только по авто-сохранению:

```text
/memory-autosave-status
```

Для AI-агента также доступен инструмент:

```text
memory_autosave_status
```

Автоматическое сохранение не требует команды. Команды статуса только показывают состояние.

## 4. Установка на Windows

### 4.1. Подготовка

1. Установи актуальный OpenCode.
2. Установи Bun и проверь `bun --version` в PowerShell.
3. Распакуй ZIP-архив так, чтобы рядом с `Install-Orchestrator.ps1` находилась папка `.opencode`.
4. Перейди в корень проекта, в который нужно установить плагины.

### 4.2. Запуск установщика

Из корня проекта выполни:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\AI-Development-Orchestrator\Install-Orchestrator.ps1
```

Если архив распакован прямо в корень пакета и скрипт лежит в текущем каталоге, используй:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\Install-Orchestrator.ps1
```

Установщик:

- создаёт `.opencode` при необходимости;
- делает резервную копию заменяемых каталогов и agent profile в `.orchestrator-backup-<дата-время>`;
- сохраняет пользовательские значения существующего `memory.config.json`;
- переносит совместимые старые значения из `orchestrator.config.json` в `memory.config.json`, если отдельного файла памяти ещё нет;
- добавляет недостающие значения `memory.autoSave` в `orchestrator.config.json`, не затирая существующие настройки;
- копирует Memory Intelligence Core и два plugin-каталога;
- выполняет `bun install` из `.opencode`.

Если Bun не найден, установи его, затем выполни:

```powershell
cd .opencode
bun install
```

### 4.3. Настройка OpenRouter

В `.opencode/memory.config.json` задаются embedding- и intelligence-модели. Пример общей секции ключа:

```json
{
  "providers": {
    "openrouter": {
      "apiKey": "sk-or-v1-ВАШ_КЛЮЧ"
    }
  }
}
```

Ключ можно переопределить отдельно в `embedding.apiKey` и `intelligence.apiKey`. Приоритет: ключ соответствующей секции → `providers.<provider>.apiKey` → переменная окружения `apiKeyEnv`.

Не коммить конфиг с API-ключом в Git. Добавь `.opencode/memory.config.json` в `.gitignore` или используй переменные окружения.

### 4.4. Перезапуск и проверка

Полностью перезапусти OpenCode. Убедись, что загружены plugin IDs:

```text
memory-intelligence
ai-development-orchestrator
```

Выполни `/memory-status`, затем `/orch-status`. Создай тестовую запись и найди её:

```text
/memory-search проверить сохранение тестовой записи
```

## 6. Все slash-команды AI Development Orchestrator

Orchestrator использует ту же память и добавляет управление разработкой.

| Команда | Аргументы | Назначение |
|---|---|---|
| `/orch-status` | — | Краткий статус проекта, задач, сессий и памяти. |
| `/orch-memory` | `<query>` | Поиск по общей памяти, удобный для задач разработки. |
| `/orch-checkpoint` | — | Ручной checkpoint от имени Orchestrator. |
| `/orch-ingest-session` | — | Импортировать полную историю текущей/давно начатой сессии, проанализировать и построить дерево задач. |
| `/orch-report` | — | Расширенный отчёт проекта. |
| `/orch-consolidate` | — | Согласованная консолидация memory entries и знаний. |
| `/orch-intelligence` | — | Отчёт Memory Intelligence через Orchestrator. |
| `/orch-state` | `<ISO timestamp>` | Историческая реконструкция состояния проекта. |

### Основной сценарий для существующей сессии

Открой давно начатую сессию и выполни:

```text
/orch-ingest-session
```

Команда:

1. определяет заголовок и ID текущей OpenCode-сессии;
2. читает сохранённую историю из локальной OpenCode SQLite в read-only режиме (V2 `session_message`/`session_part` и известные legacy-таблицы); CLI export выступает резервным вариантом;
3. дополняет историю доступными ранее сохранёнными checkpoint и текущим plugin context;
4. сохраняет исходный набор сообщений до отправки в intelligence-модель;
5. делит транскрипт на части и извлекает знания;
6. строит дерево главной задачи и подзадач, критерии приёмки, приоритеты и зависимости;
7. связывает задачи, сессию, решения и найденные объекты памяти;
8. выводит отчёт в той же сессии.

Команда не создаёт новую главную сессию. Если OpenCode не предоставляет полный транскрипт, результат явно отмечается как partial. Повторный запуск для идентичного набора данных идемпотентен.

## 9. Как работает дедупликация объектов знаний

Deduplication выполняется независимо от проверки полного хэша транскрипта.

### 9.1. Сущности

Сущности нормализуются по имени (Unicode NFKC, нижний регистр, нормализация пробелов). Проверяется совпадение как с каноническим именем, так и с уже известными псевдонимами. Например, `OpenAI`, `OpenAI Inc.` и ранее зарегистрированный alias `OpenAI` могут быть сведены к одной сущности. Совпавшая сущность обновляет aliases, confidence и last-seen, а не создаёт новую запись. Новое подтверждение записывается в `knowledge_entity_evidence` с ID extraction и сессией-источником.

### 9.2. Факты (claims)

Проверяется комбинация:

- проект;
- субъект/сущность;
- predicate;
- нормализованное значение объекта;
- временная совместимость интервалов действия.

Если такой факт уже есть, новый claim не создаётся. Predicate и object сравниваются после Unicode NFKC, приведения регистра и схлопывания пробелов. Новая транскрипция добавляется в `knowledge_claim_evidence`, а новый memory-источник связывается с прежним claim отношением `reaffirms_claim`.

Если значение отличается, но субъект и predicate совпадают, исходный и новый факт сохраняются, а система может создать `knowledge_conflicts`. Разные значения не удаляются и не объединяются автоматически.

### 9.3. Решения

Для активных решений проверяется нормализованное совпадение заголовка и текста решения. Повторное решение не создаётся, но новый memory-источник связывается с существующим объектом через `knowledge_decision_evidence` и ребро `reaffirms_decision`.

### 9.4. Сводки и записи памяти

Записи, отправленные через `memory_write`, проходят нормализованную точную проверку по проекту, kind, title и content. Для достаточно длинных записей дополнительно включается семантическое сопоставление по vector similarity — только для того же `kind` и только при достижении `deduplication.similarityThreshold` (по умолчанию 0.92). FTS/графовое совпадение само по себе не подавляет новую запись. Если векторный сервис недоступен, запись сохраняется обычным способом, а ошибка фиксируется как fallback-событие.

При совпадении используется существующий `memoryId`; новая запись не создаётся. Новый источник добавляется в `memory_entry_evidence`, обновляется подтверждение importance/confidence, а связь с текущей сессией/задачей добавляется в граф знаний. Исходный контент и evidence не переписываются.

### 9.5. Список, забывание и восстановление

`memory_list` и `/memory-list` показывают активные записи и их ID. `memory_forget` / `/memory-forget` делают soft-delete: объект исключается из FTS/vector recall и обычной выдачи, но исходные данные остаются в SQLite для восстановления и аудита. Это не безопасное физическое стирание. `memory_restore` / `/memory-restore` возвращают запись в активное состояние и восстанавливают FTS; после этого `/memory-reindex` пересоздаёт vector embeddings.

### 9.6. Источник данных не теряется

Даже при обнаружении дубликата не удаляется исходная транскрипция, checkpoint или evidence. Provenance хранится в `memory_entry_evidence`, `knowledge_entity_evidence`, `knowledge_claim_evidence` и `knowledge_decision_evidence`. Дедупликация объединяет повторное обнаружение с существующим объектом, но сохраняет ссылки на новые источники сведений. Дубликат факта с тем же значением не следует путать с новым фактом, содержащим другое значение: второе утверждение сохраняется и может породить конфликт.

## 10. Автоматические lifecycle-функции

### 10.1. Перед compaction

V2 hook `ctx.session.hook("compaction", ...)` сохраняет доступный OpenCode hook transcript в checkpoint до того, как OpenCode сформирует continuation summary. При разрешённой удалённой обработке может запускаться извлечение знаний.

### 10.2. После завершения взаимодействия

V2 события `session.execution.succeeded`, `session.execution.failed` и `session.execution.interrupted` (а также совместимый `session.idle`) вызывают проверку token threshold. Только если с момента предыдущего успешного автосохранения набрано не меньше `tokenThreshold`, создаётся новый auto-save run. В актуальном V2 event envelope session ID находится в `event.data.sessionID`; старое поле `properties` поддерживается как fallback.

### 10.3. Подстановка памяти в контекст агента

Hook `context` извлекает последний authored user prompt из V2 `event.messages`, санитизирует его и выполняет hybrid recall по этому запросу. В контекст включаются ограниченное число наиболее релевантных записей, активные решения, актуальные claims и несколько открытых конфликтов. Повторный запрос в tool-loop кэшируется на короткий срок. Режимы `relevant`, `recent` и `both` настраиваются в `memory.config.json`. При сбое semantic recall можно включить fallback на недавние записи; сам запрос агента не блокируется из-за недоступности памяти.

### 10.4. События

OpenCode events сохраняются в таблице `events`. Для авто-сохранения используются события:

- `SESSION_AUTO_SAVE_COMPLETED` — сохранение и анализ завершены;
- `SESSION_AUTO_SAVE_FAILED` — ошибка во время обработки;
- `SESSION_AUTO_SAVE_SKIPPED` — история недоступна или недоступен подсчёт токенов при отключённой оценке.

## 11. Конфиденциальность и обработка данных

- Исходные checkpoints хранятся локально в `.orchestrator/orchestrator.sqlite`.
- При включённом `intelligence.allowRemoteProcessing` фрагменты транскрипта отправляются на настроенный удалённый endpoint (например, OpenRouter) для извлечения знаний.
- Если удалённая обработка запрещена, исходная транскрипция сохраняется, но интеллектуальное извлечение пропускается.
- Единый best-effort redaction работает на границах сохранения событий, checkpoints, memory entries, данных model extraction и перед context injection. По умолчанию удаляются распространённые API/provider tokens, bearer/JWT, GitHub/Slack/AWS/Google credentials и содержимое `<private>...</private>`.
- Это не полноценный DLP: regex может пропустить неизвестный формат или секрет без распознаваемой сигнатуры. Проверь содержимое перед удалённой обработкой; не полагайся на redaction как на гарантию безопасной передачи.
- Секреты, которые уже были сохранены до установки обновления, автоматически не переписываются. При необходимости проведи аудит и вручную забудь/пересоздай соответствующие записи.
- Не отправляй в удалённую модель конфиденциальные данные, если политика проекта это запрещает.
- Файл `.opencode/memory.config.json` может содержать API-ключ. Не публикуй его в Git.
- Рекомендуется исключить из Git как минимум:

```gitignore
.opencode/memory.config.json
.orchestrator/
.orchestrator-backup-*/
```

Папку `.opencode` целиком исключать не обязательно: в ней могут находиться плагины и безопасные конфигурационные defaults. Лучше исключать только файл с секретами.

## 12. Настройки Recall, Privacy и Deduplication

Параметры провайдера и поведения памяти находятся в `.opencode/memory.config.json`. Порог автоматического сохранения сессии по-прежнему хранится в `.opencode/orchestrator.config.json` в `memory.autoSave.tokenThreshold`.

```json
{
  "privacy": {
    "redactCredentials": true,
    "redactPrivateTags": true
  },
  "deduplication": {
    "enabled": true,
    "similarityThreshold": 0.92
  },
  "recall": {
    "enabled": true,
    "mode": "relevant",
    "maxMemories": 6,
    "maxContextChars": 10000,
    "cacheMs": 15000,
    "includeRecentFallback": true
  }
}
```

### Recall

- `enabled`: включить автоматическую подстановку памяти на `context` hook.
- `mode`: `relevant` — только найденное по запросу; `recent` — последние записи; `both` — релевантные и недавние.
- `maxMemories`: максимум найденных воспоминаний (0–20).
- `maxContextChars`: лимит символов всего context pack.
- `cacheMs`: кэш одного и того же пользовательского запроса в рамках сессии (0–120000 мс).
- `includeRecentFallback`: если семантический поиск не дал результатов или завершился ошибкой, подставлять недавние записи.

### Privacy

- `redactCredentials`: redact типовые API-ключи, bearer/JWT, ключи провайдеров и популярные токены сервисов.
- `redactPrivateTags`: заменять содержимое `<private>секрет</private>` на заглушку до сохранения/передачи.

### Deduplication

- `enabled`: включить семантическое сравнение длинных записей.
- `similarityThreshold`: минимальная cosine similarity (0.70–0.999; default 0.92). Повышение порога уменьшает риск объединения разных утверждений. Семантическое совпадение проверяется только между записями одного kind.

После изменения конфигурации перезапусти OpenCode. В `/memory-status` видны текущие параметры privacy, deduplication и recall.

## 13. Частые рабочие сценарии

### Сценарий A. Начать работу с проектом

1. Выполни `/orch-status`.
2. Зарегистрируй проект через `orchestrator_project_register`, если он ещё не зарегистрирован.
3. Сформулируй основную задачу через `orchestrator_task_create`.
4. Продолжай работать с любым агентом: его контекст будет обогащаться Memory Intelligence.

### Сценарий B. Продолжить давно начатую сессию

1. Открой прежнюю OpenCode-сессию.
2. Запусти `/orch-ingest-session`.
3. Проверь созданное дерево задач и зависимости.
4. Выполни `/orch-status` и `/memory-intelligence`.
5. Дальнейшие завершённые фрагменты будут попадать в авто-save при пересечении token threshold.

### Сценарий C. Работа длится несколько часов

1. Убедись, что `memory.autoSave.enabled=true`.
2. Настрой `tokenThreshold`, например 50000.
3. Не требуется вручную вызывать checkpoint каждые N сообщений.
4. После завершённых ответов автосохранение проверяет накопление токенов.
5. В любой момент проверь `/memory-autosave-status`.

### Сценарий D. Сменить embedding-модель

1. Измени `embedding.model` и нужные параметры в `.opencode/memory.config.json`.
2. Перезапусти OpenCode.
3. Выполни `/memory-status`.
4. Выполни `/memory-reindex` до обработки ожидающих частей.
5. Убедись, что семантический поиск снова использует векторный канал.

### Сценарий E. Раздать работу дочерним агентам

1. Создай независимые подзадачи с зависимостями.
2. Используй `orchestrator_session_spawn` для каждой подходящей подзадачи.
3. Передавай дочерней сессии один ограниченный scope, критерии приёмки и контекст.
4. Проси дочернюю сессию сохранять устойчивые результаты через `memory_write`.
5. Фиксируй итог через `orchestrator_task_update`.

### Сценарий F. Проверить противоречивые требования

1. Выполни `/memory-conflicts`.
2. Изучи исходные evidence и даты.
3. Не выбирай автоматически более свежее утверждение без проверки контекста.
4. Разреши конфликт через `memory_conflict_resolve`, указав основание и при необходимости `acceptedClaimId`.

### Сценарий G. Восстановить прошлое состояние

1. Выполни `/memory-state <дата>`.
2. Для вопроса «что система знала в тот момент?» используй инструмент `memory_state_at` с `knownAt`.
3. Для вопроса «что фактически действовало на тот момент?» используй `asOf`.

## 14. Диагностика и устранение ошибок

### Плагины не появились после установки

- Убедись, что `.opencode/plugins/memory-intelligence/index.ts` и `.opencode/plugins/ai-development-orchestrator/index.ts` существуют.
- Запусти `bun install` в `.opencode`.
- Полностью перезапусти OpenCode.
- Проверь ошибки импорта `@opencode/plugin` и workspace dependency `opencode-memory-intelligence-core`.

### В `/memory-status` нет embedding-векторов

- Проверь `embedding.provider`, `embedding.model`, `embedding.baseUrl`.
- Проверь API-ключ, его приоритет и доступность модели в API каталоге.
- Убедись, что `sqlite-vec` загружается.
- Запусти `/memory-reindex`.

### Auto-save не срабатывает

1. Выполни `/memory-autosave-status`.
2. Убедись, что `enabled=true`, `checkOnSessionIdle=true`.
3. Проверь `tokenThreshold`; на тесте временно можно поставить `1000`.
4. Убедись, что OpenCode публикует `session.execution.succeeded` / `session.execution.failed` / `session.execution.interrupted` или совместимый `session.idle`; в V2 session ID читается из `event.data.sessionID`.
5. Проверь, что путь к OpenCode DB разрешается (`opencode db path`) и запись сессии видна в `session_message` или legacy-таблицах.
6. Если провайдер не публикует usage, установи `estimateFallback=true`.
7. Проверь, что `intelligence.allowRemoteProcessing=true`, если ожидается извлечение объектов через OpenRouter.
8. Просмотри логи `[memory-intelligence]`.

### В контекст не подставляется релевантная память

- Убедись, что `recall.enabled=true` в `.opencode/memory.config.json`.
- Для семантического режима проверь `/memory-status`, embedding API и наличие проиндексированных chunks.
- Для проверки временно выставь `recall.mode="both"` и `includeRecentFallback=true`.
- Учитывай `cacheMs`: повторный запрос может использовать прежний context pack в пределах срока кэша.
- Посмотри события `MEMORY_RECALL_FAILED` и `MEMORY_CONTEXT_INJECTED` в отчёте/логах.

### Секрет не попал в redaction

Redaction — best-effort. Не используй его как основание для передачи чувствительных данных в удалённую модель. Добавь сигнатуру конкретного секрета в `privacy.ts`, покрой её `smoke-test-privacy.ts` и проверь до развёртывания.

### Checkpoint сохраняется, но знания не извлекаются

- Исходная транскрипция может сохраниться даже при отключённой удалённой обработке или ошибке API.
- Проверь `intelligence.enabled`, `intelligence.allowRemoteProcessing`, ключ и модель в `memory.config.json`.
- Сравни `memory_autosave_status` и `memory_intelligence_status`.
- Для повторной обработки используй `memory_intelligence_extract` или повтори auto-save после исправления API.

### Повторный объект не появился как новая запись

Это ожидаемое поведение для дубликата. Новый источник должен появиться в `knowledge_claim_evidence` / `knowledge_decision_evidence` и в графовых связях `reaffirms_claim` / `reaffirms_decision`. Новая противоречащая формулировка, наоборот, должна создать отдельный claim и при пересечении временных интервалов — конфликт.

## 15. Локальные тесты

Из `.opencode`:

```powershell
bun install

cd packages\memory-intelligence-core
bun run test:shared-client
bun run test:vector
bun run test:intelligence
bun run test:auto-save

cd ..\..\plugins\ai-development-orchestrator
bun run test:ingest
```

`test:auto-save` проверяет:

- подсчёт агрегированной session usage, message-level provider usage и пороговый переход;
- резервную оценку текста;
- выделение сообщений после последнего сохранённого cursor;
- разбиение транскрипта на ограниченные фрагменты;
- сохранение checkpoint и курсора автосохранения;
- идемпотентность повторного запуска с тем же хэшем транскрипта;
- точное подавление дубля обычной memory entry и сохранение повторного источника;
- дедупликацию сущностей по имени и aliases;
- дедупликацию фактов по subject/predicate/object и временному интервалу;
- дедупликацию решений по нормализованным заголовку и тексту;
- запись evidence для повторных обнаружений.

Дополнительно проверь на тестовом OpenCode-проекте:

1. Поставь `tokenThreshold=1000`.
2. Создай несколько больших запросов/ответов, чтобы перешагнуть порог.
3. Заверши текущий ход агента: плагин проверяет порог на terminal event выполнения; `session.idle` поддерживается как fallback.
4. Проверь `/memory-autosave-status`.
5. Повтори тот же вопрос и решение: новые сущности/claims/decisions не должны создаваться, но должны связываться с новым evidence.
6. Создай намеренно противоречивое решение и проверь, что объект не потерян, а создан conflict.
7. Верни порог к желаемому значению, например `50000`.

Полный тест интеграции необходимо выполнить на реальной установке Bun + OpenCode и действительном API ключе. Статические проверки сами по себе не подтверждают runtime-поведение провайдера или все разновидности базы OpenCode.

## 17. Итоговая модель использования

- **Memory Intelligence** отвечает за память: запись, поиск, embeddings, Knowledge Graph, извлечение новых знаний, evidence, противоречия, checkpoint и исторические состояния.
- **AI Development Orchestrator** отвечает за выполнение работы: проекты, задачи, зависимости, сессии, декомпозиция и дочерние агенты.
- **Автоматическое сохранение** срабатывает при пересечении заданного token threshold и сохраняет полную исходную транскрипцию перед анализом.
- **Дедупликация** не удаляет источники: она предотвращает повторное создание того же объекта, добавляя ссылку на новое доказательство.

Для большинства рабочих сессий достаточно настроить порог один раз, а затем использовать `/orch-ingest-session` для импорта старых сессий и обычные инструменты обоих плагинов для дальнейшей работы.
